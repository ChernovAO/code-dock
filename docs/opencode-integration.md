# Интеграция с opencode

Документ фиксирует, что умеет API opencode V2 и как оно ложится на требования Code Dock. Требования: [functional-requirements.md](functional-requirements.md). Контекст: [overview.md](overview.md). План прототипа и результаты проверок: [prototype-plan.md](prototype-plan.md).

Источники:
- Клиент: https://opencode.ai/v2/docs/build/client
- OpenAPI: https://opencode.ai/v2/openapi.json (проверено 2026-10-21)

Версия opencode зафиксирована: **2.1.2** (`apps/opencode/Dockerfile`). Всё ниже относится к ней. При смене версии права и политики нужно проверить заново.

Пометка «проверено» значит: проверено вживую нативным бинарником 2.1.2 (2026-10-21). Права и конфигурация проверялись в песочнице с раскладкой контейнера (`/repos`, `/etc/opencode`, `HOME=/opencode`, UID 1000). Вместо модели использовался мок-провайдер, который вызывает заданные инструменты. Сборку образов и работу в docker проверяет пользователь.

Официальный клиент `@opencode/client` сгенерирован из той же спецификации, что и HTTP API. Возможности у них совпадают. Заголовок спецификации: «Experimental HttpApi surface», версия `0.0.1`. Спецификация (144 операции) совпадает с живым сервером.

## Способы подключения

1. **Бэкенд на FastAPI ходит в opencode по HTTP.** Выбран. Git и файлы остаются в FastAPI. Клиент ручной, на `httpx2`, со своими моделями для ~25 нужных событий. Генерации клиента из OpenAPI нет. Совпадает с принципом «свой агент не пишем».
2. Фронтенд ходит в opencode напрямую через `@opencode/client`. Отклонён: на публичном VPS сложнее защитить доступ к opencode.
3. Node-сервис между ними. Отклонён: добавляет третий рантайм.

FastAPI проксирует запросы и SSE-события. Фронтенд общается только с FastAPI, а авторизация решается в одном месте. Opencode работает в отдельном контейнере (`apps/opencode`) во внутренней сети docker. Порт наружу не публикуется, API закрыт Basic-паролем.

В OpenAPI полезная нагрузка SSE — непрозрачная JSON-строка. Типы событий берутся из `@opencode/client` (около 130).

## Файлы

**Решение: свой файловый слой.** FastAPI работает с файлами напрямую на общем томе `/repos`: чтение, запись, создание, удаление, переименование, загрузка, скачивание. Файловые методы opencode (`fs/*`) не используем и не проксируем.

Причины (проверено):
- `GET /api/fs/read/*` защищён: абсолютные пути и symlink наружу дают 404.
- `GET /api/fs/list` и `POST /api/experimental/fs/write` не ограничены `location`. Они принимают `../`, абсолютные пути и symlink. Через `fs/write` перезаписан файл вне репозитория.
- Запись — experimental. Удаления и переименования файлов в API нет.

Все пути в FastAPI проходят слой путей: нормализация, запрет выхода за пределы репозитория, `realpath` для symlink.

## Чаты и агент

| Что нужно | Метод API |
|---|---|
| Список, создание, переименование, удаление чатов | `session.list`, `session.create`, `session.update` (PATCH), `session.remove` |
| Отправка сообщения | `session.prompt`: поля `text`, `files`, `agents`, `skills`. Вложения через `files[].uri`, упоминание файла через `mention`. |
| История сообщений | `session.message.list`, `session.message.get` |
| Стриминг и tool calls | `GET /api/event`: живой поток всех чатов сервера (см. «События и переподключение») |
| Прерывание | `session.interrupt` |
| Подтверждение действий | `session.permission.reply` (`once`, `always`, `reject`), `session.permission.list`, `permission.request.list` |
| Модель и режим | `model.list`, `agent.list`, `session.switchModel`, `session.switchAgent` |
| Работа в фоне | `session.active`, `session.wait`, `session.inbox.*` |
| Форк чата | `session.fork` |
| Сжатие контекста | `session.compact` |

### Создание чата

`session.create` принимает `location.directory` и `permissions`. Проверено:
- `location.directory` — абсолютный путь папки проекта, например `/repos/notes/research`.
- `projectID` одинаков для всех проектов одного репозитория и отличается между репозиториями. `subpath` — путь проекта от корня репозитория. Для проекта в корне поля нет.
- `permissions` чата вычисляются последними и перекрывают конфиги и правила агента.
- Не проверено: фильтры `session.list` (`directory`, `project`, `subpath`, `search`) и пустой репозиторий без коммитов.

### Разрешения

Запрос разрешения (`GET /api/session/{id}/permission`, событие `permission.asked`) содержит `id`, `sessionID`, `action`, `resources`, `save` (шаблоны для «всегда») и `source` (сообщение и вызов инструмента). Проверено:
- `once` выполняет вызов. `reject` с `message` отдаёт модели этот текст как ошибку инструмента, без него — «The user declined this tool call». Цикл агента продолжается: модель может вызвать другой инструмент и получить новый запрос.
- `always` сохраняется на уровне репозитория. Решение действует во всех проектах репозитория и в новых чатах, в другом репозитории агент снова спрашивает. Список: `GET /api/permission/saved?projectID=<id>`.
- Автоотклонения по таймеру в opencode нет (по документации). Его делает FastAPI. Не проверено: каскад `reject` (по документации отклоняет все ожидающие запросы чата).

Инструмент `question` (проверено): сначала приходит запрос разрешения (`question`, `*`), затем создаётся форма (`GET /api/session/{id}/form`, ответ `POST .../form/{formID}/reply`), и чат ждёт ответа. UI должен поддержать формы либо `question` нужно запретить правилом.

## События и переподключение

Формат (проверено):
- `GET /api/event` отдаёт кадры только с `data:` (JSON). Полей SSE `id:` и `event:` нет, хотя в OpenAPI они описаны. Приходит также комментарий `: heartbeat`. Первое событие — `server.connected`.
- Поток общий для всех чатов и репозиториев сервера. Событие несёт `id` (`evt_…`), `type`, `created`, `location` и `data` (в нём `sessionID`). Фильтровать по чату нужно в FastAPI.
- Долговечные события несут ещё `durable: {aggregateID, seq, version}`. `seq` растёт внутри чата с нуля. Эфемерные его не имеют: `permission.asked`, `permission.replied`, `session.text.delta`, `session.usage.updated`, `project.updated`.
- Типы, которые наблюдались: `session.created`, `session.inbox.enqueued`, `session.execution.started` и `.succeeded`, `session.step.started` и `.ended`, `session.tool.input.started` и `.ended`, `session.tool.called`, `session.tool.success`, `session.text.started`, `.delta` и `.ended`, `session.renamed`, `permission.asked`, `permission.replied`.
- По спецификации подписка «volatile by contract»: медленный потребитель переполняет поток, и тот обрывается. События во время разрыва теряются.

**Докачка через журнал не работает** (проверено). `GET /api/experimental/session/{id}/log?after=<seq>` не отдаёт ни прошлых, ни живых событий, в том числе с `follow=true`. Приходит только служебный кадр `log.synced` с последним `seq`. Таблица `event` в БД opencode пуста: события не сохраняются, чат хранится в проекции `session_message`. Схема «`id: <seq>` и `Last-Event-ID`» не применима.

Схема работы с чатом:
1. Открыть поток `/api/event`, затем прочитать историю `session.message.list`.
2. Слить их идемпотентно. Большинство долговечных событий несут полное состояние (`session.text.ended` — весь текст, `session.tool.success` — результат), поэтому повторы безвредны.
3. После обрыва повторить с шага 1 целиком.

Дельты текста, рассуждений и ввода tool эфемерны. Недостающее досылает `session.text.ended`. Буфера событий в FastAPI нет.

## Права и граница агента

Правила лежат в образе: `apps/opencode/opencode.jsonc` попадает в `/etc/opencode/opencode.jsonc`. Системный конфиг перекрывает глобальный и репозиторный, а политики из него не отменяет никто, кроме Console и MDM (проверено: репозиторные политики `allow` системные `deny` не снимают). Про Console см. «Ограничения и риски».

| Область | Поведение |
|---|---|
| Чтение, поиск, правка | Без вопросов: `read`, `glob`, `grep`, `edit` |
| `.env` | `read` для `*.env` и `*.env.*` спрашивает, `*.env.example` без вопроса |
| Остальное | Спрашивает (`* * ask`). Проверено для `shell`, `webfetch`, `websearch`, `subagent`, `question`. |
| Code Mode (`execute`) | Запрещён правилом `permissions`, инструмент пропадает у модели |
| Выход за репозиторий | Запрещён политикой `external_directory:*`. Соседние проекты того же репозитория доступны. |
| Правка `.git` | Запрещена политиками `edit:.git/*` и `edit:*/.git/*` |
| Плагины и MCP | Запрещены политиками `integration.use` (`plugin:*`, `mcp:*`) |
| Режим `plan` | Правка запрещена правилом агента |

### Порядок правил

Побеждает последнее подходящее правило. Проверено через `GET /api/agent`: базовая политика (`* * allow`, правила для `.env`) → встроенные правила агента → правила из конфигов (от низшего приоритета к высшему) → правила агентов из конфигов → `permissions` чата. Следствия:
- Глобальные правила конфига перекрывают встроенные правила агентов. Поэтому `edit * allow` отменил бы запрет правок у `plan`, и в конфиге есть отдельное правило для `plan`. Встроенные ограничения `explore` и `general` (запрет правок, `question`, `subagent`) перекрыты так же. Эти агенты запускаются только через `subagent`, который спрашивает.
- Политики вычисляются отдельно и в обратном порядке: системные последними.

### Формат ресурсов

Проверено:
- `read` и `edit` внутри репозитория: путь **относительно `location`** без `./`. Абсолютный путь от модели нормализуется: `notes.md`, `../projectY/a.md`, `../.env`. Если проект лежит в корне репозитория, правка `.git/config` выглядит как `.git/config`, иначе как `../.git/config`. Поэтому для `.git` нужны два шаблона.
- Вне репозитория: канонический абсолютный путь. Сначала проверяется `external_directory`.
- `shell`: текст команды. Составная команда даёт несколько ресурсов, шаблоны для «всегда» — префиксы (`echo *`).
- `webfetch`: URL. `websearch`: запрос. `subagent`: ID агента. `question`: `*`.
- Политика `tool.use`: ресурс `<действие>:<значение>`, например `edit:.git/*`.

### Что не защищено

Проверено, конфигом не закрывается:
- **Symlink внутри репозитория.** Граница работает по лексическому пути. `read` читает цель symlink на `/etc/passwd` или на чужой репозиторий, `write` пишет через него в чужой репозиторий и в `.git/config`. Клонировать нужно только доверенные репозитории.
  - Не проверено, следует из проверенного: так же без вопроса читаются БД opencode `/opencode/.local/share/opencode/opencode.db` с ключами провайдеров и `/proc/self/environ` с `OPENCODE_SERVER_PASSWORD`. Враждебный репозиторий с такими ссылками отдаёт секреты в контекст модели.
  - Сам агент symlink создать не может: для этого нужен `shell`, а он спрашивает. Опасны symlink, пришедшие с клоном или pull.
- **`shell`.** Из границы проверяется только `workdir`. Команды `cat /etc/passwd`, `ls /repos/other`, `echo x > /repos/other/x` только спрашивают разрешение. Защита здесь — внимание пользователя.
- **`.env` защищён только от прямого `read`.** `grep` читает его без вопроса, в том числе скрытые файлы.
- **Полный вывод длинной команды** `shell` сохраняется в `/opencode/.local/share/opencode/shell/…`. Агент прочитать его не может (запрет внешнего каталога). Исключение открыло бы вывод чужих репозиториев.

### Code Mode

Инструмент `execute` не проходит проверку разрешений на вызове (проверено). Внутри доступны `fetch` в любую сеть и `tools.opencode.*`. Агент без вопросов сходил на внешний сайт, перенёс сессию в другой репозиторий (`session_move`) и на следующем ходу прочитал и записал там файлы, создал worktree (`worktree_create`). Закрывает только правило `permissions` `execute * deny`: инструмент пропадает из набора модели. Политика `tool.use` с `execute:*` не действует.

### Конфиг репозитория

Без `OPENCODE_DISABLE_PROJECT_CONFIG=1` репозиторные `opencode.jsonc` и `.opencode/` выполняют код и снимают ограничения (проверено):
- `formatter` запускает команду при записи подходящего файла. Политики это не закрывают.
- Плагины из `.opencode/plugins/` и MCP-серверы запускаются при открытии проекта. Закрыты политиками `plugin:*` и `mcp:*`. Политики не отключают ~90 встроенных плагинов и провайдеров.
- Правила агентов из репозитория (`agents.*.permissions`, агенты из `.opencode/`) стоят после системных. Они снимают вопросы про `shell` и `webfetch` и возвращают `execute`. Политики остаются в силе.
- Не проверено, по документации: `providers.*.settings.baseURL` из репозитория может перенаправить запросы вместе с ключом.

Поэтому в образе задано `OPENCODE_DISABLE_PROJECT_CONFIG=1`: конфиги репозитория не читаются, остаются глобальный и системный. Цена: `AGENTS.md` проекта не подхватывается (по документации, проверено). Обход: `PUT /api/experimental/session/{id}/instructions/entries/{key}` с телом `{"value": "<текст>"}`. Проверено: текст попадает в промпт модели. `core` может сам читать `AGENTS.md` от проекта до корня репозитория и передавать его так. Без флага `AGENTS.md` проекта и корня репозитория подхватываются оба.

## Развёртывание opencode

Проверено по реестру образов (`ghcr.io/anomalyco/opencode:2.1.2`, amd64 и arm64):
- Alpine 3.24.2 (musl). Бинарник `/usr/local/bin/opencode`, `ENTRYPOINT ["opencode"]`, без `CMD` и порта. Работает от root, `WorkingDir` — `/`.
- `ripgrep` в образе есть, `git` и `bash` нет: их ставит `apps/opencode/Dockerfile`.
- UID и GID 1000 свободны. Пользователь `app` создаётся с UID и GID хоста, чтобы файлы в `/repos` принадлежали владельцу репозиториев. Запись в `passwd` нужна и git.
- Каталог `/etc/opencode` создаётся в `RUN` с режимом 755 до `COPY --chmod=644`. Иначе `--chmod` выставляет 644 и каталогу, `app` не может в него зайти, и opencode молча работает без системного конфига: без прав и политик образа (проверено в docker). Признак — в `GET /api/config` нет документа `/etc/opencode/opencode.jsonc`. Ловит `apps/opencode/verify/live.py`.
- Сборка образа запускала opencode от root, поэтому `/tmp/opencode` принадлежит root. Это не мешает (проверено: каталог остаётся пустым).

Данные при `HOME=/opencode` (том `opencode-data`, проверено): БД с чатами и ключами провайдеров в `/opencode/.local/share/opencode/opencode.db`, там же логи, снапшоты и выводы команд. Кэш — `/opencode/.cache/opencode`, пользовательский конфиг — `/opencode/.config/opencode/`.

Пароль (проверено): сервер требует Basic-авторизацию, пользователь `opencode`. `OPENCODE_SERVER_PASSWORD` фиксирует пароль. Неверный пароль, другое имя пользователя и запрос без авторизации дают 401, включая `/openapi.json`. Статичная страница `/` отдаётся без пароля. Клиент CLI тоже читает `OPENCODE_SERVER_PASSWORD`.

Провайдер (проверено): `opencode auth login <провайдер> --method key --server http://127.0.0.1:4096` сохраняет ключ в БД, провайдер появляется на сервере без перезапуска. ID `opencode` подключает не провайдера модели, а OpenCode Console по ключу сервисного аккаунта (проверено в контейнере, `auth list` показывает `OpenCode Console`). Другие способы — переменные окружения провайдера и конфиг `providers`.

## Git и откат

Есть в API:
- `vcs.status`, `vcs.diff`, `vcs.branch.list`, `vcs.get`, `vcs.init`.
- `session.diff`: изменения по ходам сессии.
- Откат правок агента: `session.revert.stage` (параметры `messageID`, `files`), затем `session.revert.commit` или `session.revert.clear`.
- `worktree.create`, `list`, `remove`: возможная основа для веток.

**Нет в API** (остаётся на FastAPI): `commit`, `push`, `pull`, `clone`, история коммитов. Для них нужен `git` через `subprocess` или pygit2/GitPython.

По документации, не проверено: снапшоты лежат в отдельной git-базе в каталоге данных opencode и не трогают коммиты и индекс. Откат совместим с ручными коммитами, но перезаписывает текущие правки файлов, которые трогал агент. Откат запрещён, пока чат выполняется.

## Дополнительные возможности

- `session.generate`, `experimental.generate.text`: генерация текста, например сообщения коммита.
- `experimental.session.export` и `import`: экспорт и импорт сессии. Возможная основа для сохранения истории чатов в репозиторий.
- `experimental.voice.session`: возможная основа для голосового ввода. Не проверено, в первой версии не используем.
- `POST /api/pair` и `GET /auth/connect/{code}`: сопряжение по коду. Возможный способ авторизации телефона. Не проверено.
- `provider.*`, `integration.*`, `credential.*`: настройка провайдеров, включая OAuth.
- `pty.*`, `persistent-pty`: терминал. Для проекта не нужен.

Поиска по истории чатов в API нет. Нужен перебор `session.list` и `message.list` или свой индекс.

## Ограничения и риски

- **События без replay.** Подписки `/api/event` работают только вживую. Журнал сессии для докачки непригоден. После обрыва подписка заново и полное перечитывание истории. См. «События и переподключение».
- **Нестабильность API.** Спецификация названа экспериментальной. Версия opencode зафиксирована в образе.
- **Запись вне проекта.** Своя файловая логика в FastAPI, см. «Файлы».
- **Безопасность агента.** Агент выполняет команды и правит файлы. Граница и её дыры описаны в «Права и граница агента».
- **Общий том.** Через `shell` (после одобрения) агент достанет до всех репозиториев в `HOST_REPOS_DIR`. Использовать выделенную папку, а не `~/code`. Жёсткая изоляция потребовала бы монтировать один репозиторий.
- **GitHub PAT** живёт только в `core`. В `remote`-URL и `.git/config` его писать нельзя: он окажется на общем томе и будет виден агенту. Передавать на время команды через `GIT_ASKPASS` или `http.extraheader`.
- **Хуки и конфиг git.** Агент мог бы подложить `.git/hooks/*`, которые выполнит `core`. Закрыто политикой `edit:.git/*` и вызовом git в `core` с `-c core.hooksPath=/dev/null`. Но политику можно обойти через symlink (см. «Что не защищено»), а git исполняет команды не только из хуков, но и из `.git/config`: `core.fsmonitor`, `core.sshCommand`, `credential.helper`, `filter.*`, `diff.external`. Для `core` эти риски не закрыты.
- **OpenCode Console.** По документации opencode, Console управляет конфигом организации и может отменять системные политики образа. Тогда граница агента держится не на `apps/opencode/opencode.jsonc`, а на настройках организации в Console. Подключается командой `opencode auth login opencode`. Как Console доставляет конфиг, не проверено: в OpenAPI 2.1.2 про это ничего нет. После подключения и после изменений в Console проверяйте контейнер скриптом `apps/opencode/verify/live.py`. Он сверяет документы конфига (`GET /api/config`) и итоговые правила агентов (`GET /api/agent`) с образом. Политики, которые применяются вне конфига, скрипт не видит.
- **Сеть.** Не ставить `internal: true`: иначе opencode не достучится до провайдеров. Порт opencode наружу не публикуется.
- **Хранение сессий.** Сессии лежат в БД opencode в томе `opencode-data`. `docker compose down -v` удалит том вместе с чатами и ключами провайдеров. Репозитории на хосте он не затронет. Нужен бэкап.

## Что проверить на практике

1. Поведение `fs/read` и `fs/write` на путях за пределами проекта и на symlink. **Проверено**, см. «Файлы».
2. Формат событий в `/api/event`: типы для стриминга текста, tool calls и запросов разрешений. **Проверено**, см. «События и переподключение». Каскад `reject` не проверен.
3. Совместимость `session.revert` с ручными git-коммитами. Не проверено.
4. Работа `experimental.voice.session` для голосового ввода. Не используем.
5. Механизм pairing как вариант авторизации. Не проверено.
6. Привязка проекта (папки в репозитории) к `location` и изоляция сессий разных проектов. **Частично**: `location` — папка проекта, `projectID` и `subpath` проверены, фильтры `session.list` и пустой репозиторий нет.
