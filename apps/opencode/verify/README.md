# Стенд проверки образа opencode

Стенд проверяет `apps/opencode`: Dockerfile, системный конфиг с правами и политиками и поведение opencode на нативном бинарнике той же версии. Docker не нужен: песочница `bwrap` повторяет раскладку контейнера (`/repos`, `/opencode`, `/etc/opencode`, UID 1000). Сборку образа и работу в контейнере стенд не проверяет: конфиг в песочницу монтируется как JSON, права файлов образа не воспроизводятся. Собранный контейнер проверяет `live.py` (см. ниже).

## Требования

- Linux и `bwrap` (bubblewrap).
- `git`: нужен для тестовых репозиториев и самого opencode.
- Нативный opencode **2.1.2**, как в `apps/opencode/Dockerfile`. Путь задаётся через `--binary`, переменную `OPENCODE_BIN` или `opencode` из `PATH`. Версия сверяется с тегом Dockerfile.
- `rg`: берётся из `PATH` или `~/.cache/opencode/bin/rg`. Если не найден, opencode скачает его сам (нужна сеть).
- Python 3.14 (`.python-version`). Сторонние пакеты не нужны.

`docker compose` нужен только для статической проверки `compose.yaml`. Если его нет, проверка пропускается.

## Запуск

Из корня репозитория:

```sh
python3 apps/opencode/verify/run.py
```

Из каталога стенда:

```sh
cd apps/opencode/verify
python3 run.py
```

Примеры:

```sh
python3 apps/opencode/verify/run.py --profile main --only boundary
python3 apps/opencode/verify/run.py --keep
```

## Проверка работающего контейнера

`live.py` проверяет уже запущенный стек, а не образ в песочнице. Он нужен после подключения внешних источников конфига, прежде всего OpenCode Console: по документации opencode Console может отменять системные политики.

```sh
python3 apps/opencode/verify/live.py --directory /repos/<репозиторий>
```

Запросы идут из контейнера `core` через `docker compose exec`, пароль и адрес берутся из его окружения. Модель не вызывается. Проверки:
- версия сервера совпадает с `Dockerfile`, подключённые интеграции выводятся списком;
- `GET /api/config`: конфиг собран только из `/etc/opencode` и `/opencode/.config/opencode`, системные `permissions`, `policies` и `agents` загружены ровно как в `opencode.jsonc`, другие документы не задают права, политики, агентов, плагины, MCP, `formatter`, `lsp` и `enterprise`;
- `GET /api/agent`: у каждого агента есть правила системного конфига подряд, а после них — только запреты.

Агенты появляются, когда у папки есть хотя бы один чат. Если чатов нет, скрипт создаёт временный и удаляет его. Политики, которые применяются вне конфига, скрипт не видит: поведение агента проверяет `run.py`. Флаг `--url` обращается к opencode напрямую (пароль из `OPENCODE_SERVER_PASSWORD`), так скрипт проверяется на нативном сервере. Коды выхода те же, что у `run.py`.

## Флаги

| Флаг | Что делает |
|---|---|
| `--profile` | Профиль: `static`, `main`, `policy-only` или `control`. Можно повторять. По умолчанию все. |
| `--only` | Выполнять проверки, в id которых есть подстрока. Группы, которые при этом не нужны, не запускаются. |
| `--keep` | Не удалять временный каталог и напечатать его путь. |
| `--any-version` | Не требовать совпадения версии нативного opencode с Dockerfile. Для черновых прогонов: чужая версия ничего не доказывает про образ. |
| `--config` | Системный конфиг opencode. По умолчанию `apps/opencode/opencode.jsonc`. |
| `--dockerfile` | Dockerfile, из которого берутся версия и переменные `ENV`. По умолчанию `apps/opencode/Dockerfile`. |
| `--binary` | Путь к нативному opencode. Если не задан, берётся `OPENCODE_BIN` или `opencode` из `PATH`. |

## Коды выхода

- `0` — все требования выполнены. Ограничения и пропуски на код не влияют.
- `1` — есть нарушения, в том числе сбой инфраструктуры (например, сервер не стартовал).
- `2` — окружение не готово: не Linux, нет `bwrap` или `git`, не найден бинарник, версия не совпадает с Dockerfile без `--any-version`.

## Профили

| Профиль | Что проверяет | Что доказывает |
|---|---|---|
| `static` | Dockerfile: точный тег версии и `OPENCODE_DISABLE_PROJECT_CONFIG=1`. `compose.yaml`: обязательные `OPENCODE_SERVER_PASSWORD` и `HOST_REPOS_DIR`, опубликованные порты, тома. | Конфигурация образа и compose соответствует решениям. Поведение агента не проверяется. |
| `main` | Образ как есть: флаг, права и политики включены. Авторизация, состав API, загрузка конфига, границы и `.git`, `.env`, вопросы, агенты, враждебный репозиторий, инструкции, разрешения, события, провайдер и CLI. | Заявленные в документации права, политики, API и события работают на зафиксированной версии. |
| `policy-only` | Флаг отключён, права и политики остаются. Отдельно проверяются враждебный репозиторий, перекрытие правил репозитория правами чата и цена отказа от флага. | Системные политики сами закрывают плагин, MCP, выход за репозиторий и `.git`. Правила репозитория их не снимают. |
| `control` | Флаг отключён, политики `integration.use` для `plugin:*` и `mcp:*` убраны. | Детекторы работают: без защиты плагин исполняется и MCP стартует. Иначе успех `main` ничего не доказывает. |

## Требования и ограничения

- `Reporter.requirement` — требование. Нарушение увеличивает счётчик ошибок и даёт код выхода `1`.
- `Reporter.limitation` — известное ограничение из [docs/opencode-integration.md](../../../docs/opencode-integration.md), в основном из раздела «Что не защищено». На код выхода не влияет: стенд сообщает, воспроизводится дыра (`огран.`) или больше нет (`ушло`). Если ограничение ушло, обновите документацию и проверки.
- `Reporter.failure` — сбой инфраструктуры, например сервер не стартовал. Считается ошибкой всегда, даже при `--only`.
- `Reporter.skip` — проверка неприменима, например нет `docker compose`.

В `main` проверяются ограничения: symlink за пределы репозитория, `shell` с путями снаружи, `grep` по `.env`, недоступный агенту полный вывод команды и журнал сессии без replay. В `policy-only` — `formatter`, правила агента из репозитория и `AGENTS.md` без флага.

## Песочница

У каждого профиля свой каталог внутри общего временного, свои `/repos` и `/opencode`, случайный свободный порт и пароль. Сервер запускается как `opencode serve` и после профиля останавливается.

| Путь | Что это |
|---|---|
| `/repos` | Записываемый каталог с тестовыми репозиториями: `alpha` (проекты `x` и `y`), `beta`, `victim`, `links` с symlink, `hostile`, файл `loose.txt`. |
| `/opencode` | Записываемый каталог, эмулирует том `opencode-data` и `HOME`: конфиг с мок-провайдером, БД, логи, снапшоты. |
| `/etc/opencode/opencode.jsonc` | Системный конфиг профиля, только для чтения. |
| `/opt/oc/opencode` | Нативный бинарник opencode. |
| `/opt/oc/rg` | `rg` с хоста, если найден. |
| `/etc/passwd`, `/etc/group` | Пользователь `app` с UID и GID 1000. |
| `/tmp/opencode` | Пустой каталог только для чтения, как каталог, созданный root при сборке образа. |
| `/etc/resolv.conf`, `/etc/hosts` и другие файлы | Пробрасываются с хоста только для чтения. |

Пользователь — UID/GID 1000. `bwrap` поднимает user, pid, ipc и uts namespaces, окружение очищается, `PATH` — `/opt/oc:/usr/local/bin:/usr/bin:/bin`. `/tmp` — tmpfs, `/etc` — tmpfs с проброшенными файлами.

Сеть не изолируется. Мок-провайдер доступен по `127.0.0.1`, внешняя сеть тоже. Сетевую изоляцию контейнера стенд не проверяет.

## Как добавить проверку

1. Соберите промпт из строк `CALL <инструмент> <json>`. Хелперы `read`, `write`, `edit`, `shell`, `grep`, `glob` и `call` в `client.py` уже делают это. Несколько строк — несколько вызовов по порядку.
2. Отправьте промпт через `api.run(directory, calls, replies=...)`. Мок ищет промпт по `CALL`, а не по последнему сообщению пользователя: synthetic-напоминания режимов (например, `plan`) могут идти после промпта. На i-м шаге мок отвечает i-м вызовом, после последнего — текстом `done`. Если инструмента нет в `tools` запроса, вызова не будет. Результат — `Outcome.kind`: `ok`, `blocked`, `ask`, `nocall` или `error`.
3. Запишите результат. Требование, в том числе невыполненное, — `rep.requirement(id, title, ok, detail)`. Известная дыра — `rep.limitation`. Если проверить нельзя — `rep.skip`. Сбой старта сервера до проверок обрабатывает `run_profile` через `rep.failure`.

В табличных проверках добавьте `_case(...)` в список `cases`: `run_table` выполнит их параллельно и сравнит `Outcome.kind` с ожиданием. Идентификатор пишите как `<группа>.<имя>`, а блок проверок начинайте с `rep.wants(group)`, иначе он не будет учитывать `--only`.

Новый профиль — это элемент `PROFILES` в `run.py`: имя, заголовок, преобразования конфига и окружения и функция проверок.
